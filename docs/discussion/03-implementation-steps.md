# 実装ステップ（フェーズ定義）— 確定

> ステータス: **確定**（DD-020〜DD-022 として decisions.md に転記済み）
> 関連: DD-002（2 プロジェクト独立 + 契約共有）、DD-004（企業・受託スタイル）、DD-014（設計書体系）

## 全体方針

ウォーターフォール寄りの**フェーズベース進行**を基本としつつ、Phase 4 以降は各プロジェクト並走（アジャイル混合）とする。フェーズの完了条件 (Exit Criteria) を明示し、フェーズゲートでステークホルダー承認を得る。

3 プロジェクト (Backend / Web / Android) は **Phase 0〜1 は同期、Phase 2 以降は各プロジェクトのペースで並走**する。共有契約 (S1-S6) の更新は全チーム同期ポイントを設ける。

## フェーズ全体図

```
Phase 0: プロジェクト立ち上げ          [全チーム同期]
   ↓
Phase 1: 要件定義                       [全チーム同期, S1/S6 確定]
   ↓
Phase 2: 基本設計（外部設計）           [3プロジェクト並走開始, S2/S3/S4/S5 草案]
   ↓
Phase 3: 詳細設計（内部設計）           [並走, S3 OpenAPI 完成]
   ↓
Phase 4: 実装                          [並走, 単体テスト併走 (TDD)]
   ↓
Phase 5: 結合テスト                    [Backend ↔ Web / Backend ↔ Android]
   ↓
Phase 6: システムテスト                [性能・セキュリティ・受入準備]
   ↓
Phase 7: 受入テスト (UAT)              [お客様確認]
   ↓
Phase 8: リリース・運用引継            [本番デプロイ・Play Console 公開]
```

## フェーズゲートでのチェック観点

各フェーズ間の遷移時に以下を確認する:

1. **成果物の完成度**: 章立てテンプレート (DD-016) に対する充足率
2. **トレーサビリティ**: 上位要件 → 設計 → テスト の対応関係
3. **未決事項**: 残課題が次フェーズで解決可能か（解決不可能なら遡及）
4. **リスク**: X2 リスク管理表で High リスクが許容範囲か
5. **品質**: テストカバレッジ・レビュー指摘消化率

## チーム独立進行時の同期ポイント

Approach C で並走する 3 プロジェクトの**強制同期ポイント**:

| 同期点                    | フェーズ      | 内容                                          |
| ------------------------- | ------------- | --------------------------------------------- |
| 要件レビュー会            | Phase 1 末    | 全機能要件をお客様承認                        |
| API エンドポイント一覧確定 | Phase 2 中盤  | エンドポイント数・命名規約・大枠スキーマ      |
| OpenAPI v0.1.0 確定       | Phase 3 末    | フロントの orval 生成が確定スキーマで動く     |
| API 破壊変更レビュー       | Phase 4 随時 | バージョン分岐 (`/v1/`→`/v2/`) のタイミング合意 |
| 結合テスト開始             | Phase 5 開始  | 実 Backend での結合テスト準備完了             |
| UAT 開始                  | Phase 7 開始  | 全プロジェクトが UAT 環境にデプロイ済み       |

## 並走時の難所と対策

| 難所                                     | 対策                                                                                          |
| ---------------------------------------- | --------------------------------------------------------------------------------------------- |
| Backend 遅延でフロントがブロックされる   | DD-012 のモック戦略 (MSW + Prism) で Backend なしでも Phase 3-4 を進行可能                    |
| Web と Android で API 要件がぶつかる     | 全チーム合同 API レビュー (Phase 2-3) で superset として Backend に集約                       |
| OpenAPI の破壊変更でフロントが壊れる     | DD-013 の URL パスバージョニング + フロント側 CI で型生成差分検出                              |
| フロント 2 チームの実装ペース差         | フェーズゲートはプロジェクト単位で個別、お客様への報告はマイルストーン単位で揃える            |
| 非機能要件 (S6) の解釈差                | Phase 1 で具体値合意、Phase 6 のシステムテスト基準として固定                                  |
