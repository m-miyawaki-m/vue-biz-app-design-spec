# 設計書体系（成果物リスト）— 確定

> ステータス: **確定**（DD-014〜DD-019 として decisions.md に転記済み）
> 関連: DD-002（API/連携仕様書のみ共有）、DD-004（企業・受託スタイル）

## 方針

Approach C（コードベース完全分離）+ 企業・受託スタイル前提のもとで、ドキュメント体系を **共有(契約) / Backend 固有 / Web 固有 / Android 固有 / 横断** の 5 カテゴリで整理する。レビュー・トレーサビリティに耐える粒度を確保する。

| #   | 成果物                | 形式                                    | 管理                       | 主な章立て                                                                 |
| --- | --------------------- | --------------------------------------- | -------------------------- | -------------------------------------------------------------------------- |
| S1  | 業務要件定義書 (共有部分) | Markdown                              | 全チーム共同レビュー       | 業務概要・登場ロール・主要ユースケース全体像・業務フロー・用語(導入)         |

### S1 の範囲について

Approach C 厳守との整合性のため、S1 は「**業務概要・主要ロール・業務フロー大枠・用語（導入）**」までを共有範囲とし、**機能要件詳細は各プロジェクト（B1/W1/A1）に分割する**。これにより:

- 業務全体像はチーム間で共通理解
- 機能要件レベルでは各チームが独立して詳細を書く

## ドキュメント間トレーサビリティ

```
S1 業務要件 (大枠)
  ├─ B1 Backend 要件 ─→ B2 DB ─→ B5 API 処理 ─→ B6 ログ → B8 Test
  ├─ W1 Web 要件 ─→ W2 画面一覧 ─→ W3 画面設計 ─→ W5 コンポーネント ─→ W7 Test
  └─ A1 Android 要件 ─→ A2 画面一覧 ─→ A3 画面設計 ─→ A6 コンポーネント ─→ A8 Test

S3 API 仕様 (OpenAPI) ←── B5 から自動生成
                       └──→ W3/W5, A3/A6 が orval 経由で消費

S2 データ辞書, S4 認証仕様, S5 エラーコード ←── 全 B/W/A 文書から参照
S6 非機能要件 ←── B3/B4/B6/B7 で具体化、W/A はクライアント影響範囲のみ参照
```

## 章立てテンプレート方針

`docs/templates/` 配下に各文書種別のひな型を置き、Web/Android/Backend チームで共通の枠組みを使う。**Approach C 厳守でも「文書フォーマットだけは揃える」**ことで:

- レビュアーが文書間を移動するときの認知コスト削減
- 抜け漏れチェックの自動化が可能
- 後続プロジェクトへの再利用性

採用ひな型（最低限）:

- `template-requirements.md` — 要件定義書ひな型
- `template-screen-design.md` — 画面設計書ひな型
- `template-internal-design.md` — 内部設計書ひな型
- `template-test-spec.md` — テスト仕様書ひな型
- `template-api-internal.md` — API 内部処理設計書ひな型

（ひな型の実体は本プロジェクトのスコープ外。各案件で本リポを参照して各自プロジェクトに配備する想定）
